Building Photo Cruiser with Claude Code

An analysis of about 75 prompts I wrote across 35 Claude Code sessions (6–11 October 2026). Over those six days I compared technology stacks for a photo app with throwaway prototypes, then built it for real in Rust/iced. This page covers how the prompting differs from someone building software for the first time, which agentic engineering patterns came up, and the vocabulary involved.

1. How it differs from a first-time builder

Explored before committing

I built the same small feature in about 8 stacks (web File API, Electron, Tauri, COSMIC, Kitty terminal, egui, GTK4, Deno desktop, then iced) and compared them on evidence.

First-timer: picks one stack, or lets the AI pick, and is stuck with it.

Weighted criteria for my real situation

8 criteria, weighted for an app for myself, but potentially for my friends who run different OSes. I spotted that Slint is commercially licensed.

First-timer: judges by "does it work" and how it looks.

Designed for testing first

I asked which stack the agent could test fully, and for headless UI testing not based on screenshots, but in deep understanding of each individual UI part.

First-timer: tests by clicking around, after something breaks.

Chose the architecture myself

splits gui and lib, is able to be operated from cli and agents, with a spec, an MVP scope and tickets.

First-timer: asks for "an app that does X".

Protected the repo

why you updated an rs file???, why a run app should write anything there, why sudo?, Why is there so many just commands?

First-timer: rarely notices or questions side effects.

Thought about future features

Before choosing a stack I checked whether it could handle Darktable-level local contrast, sharpening and Samba shares. I still kept scope down: keep it reasonably simple.

First-timer: overbuilds now, or hits a dead end later.

Judged UX by feel

300 milliseconds are not really great… some smarter ways to improve the feel of speed. Vim keys, but dont support q, system already got closing app shortcut.

First-timer: takes the numbers or the defaults at face value.

Edited the copy

You are repeating yourself… Fast photo browser and Instant photo switching. I cut generic claims and kept the description short.

First-timer: ships AI copy as written.

Prompted in short bursts

Many prompts were y, go, commit, ship. I let the agent run and steered with one-line corrections.

First-timer: over-explains every step, or approves everything without review.

4. The prompts, condensed

Phase 1: comparing stacks (sandbox)

  1. Build one feature (open a folder, use the arrow keys to move through photos sorted by filename) as 5 prototypes: browser File API, Electron, Tauri, COSMIC, Kitty terminal. Intent file, shared spec, subagents, verify they're runnable, short README.
  2. Compare them by lines of code and complexity. Pushback: the web version makes you upload the folder.
  3. Add AVIF/HEIC support and a freehand crop with a 50% darker background to every app, using subagents.
  4. Which one can you test fully? What about Deno desktop or GTK? Native look and feel?
  5. Can they handle format conversion, Darktable-style local contrast, sharpening, Samba? Speed and re-render lag?
  6. Build egui, GTK4 and Deno desktop clones (no Bun or Flutter). Weighted HTML comparison on 8 criteria; pick a winner.
  7. Challenged the result: could egui be themed native? egui feels limiting; Slint is commercially licensed. Build the iced version and update the comparison.
  8. Write the initial spec for an iced app: GUI/lib split, operable from CLI and agents, aiwork protocol. Init git. Can iced be tested headless with real UI understanding?

Phase 2: the real app

  1. Implement the base spec: MVP first, best practices, run and verify skills, subagents.
  2. No writing to out/; use a temp folder outside the repo. What's left? Turn it into tickets, kept simple.
  3. Verify switching speed on real media; 300 ms feels slow, so add transitions and improve the feel of speed. Keep the rest in tickets, then commit.
  4. Full screen task and implementation; remove the double click. What is a render golden?
  5. README and GitHub description (cut the repetition), MIT licence, ship.
  6. Why so many just commands? Headless verification, headed on request.
  7. Window title with the full path, no em dash, a clean UI with a hidden menu, a menu shortcut, vim keys but no q.
  8. A grid as the default view, file names hidden with a toggle, and an investigation of the 3-second thumbnail delay.
  9. Justified layout reused from another repo, with margins, settings and remembered state.
  10. Machine-wide install with an icon (why sudo?), the icon placed in an About entry, and arrow-key navigation in the menu.
